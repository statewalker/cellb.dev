## What the recordings say (taken before coding)

- **`sql.exec()` with no statement at the end.** New project `sql-exec`, recorded on celld 0.6.3
  and workerd (Miniflare 4.20260730.0). Both refuse `""`, `"   "`, `";"`, a comment alone, and a
  script with a comment or an empty `;` after its last statement; both run `"SELECT 1;   "`,
  `"SELECT 1 -- c"` and `"SELECT 1;; SELECT 2"`. celld words it
  `SQL error: SQL code did not contain a statement`, workerd `SQL code did not contain a
  statement.`: celld judges, so cellb takes celld's words; `workerdDiffers` records the other.
- **`WorkerCode.compatibilityFlags`.** New project `worker-loader-flags`, three scenarios:
  - `-binary-type`: celld and workerd agree (`websocket_standard_binary_type` gives `"blob"`).
    cellb fails before that: a loaded Worker in a Node thread has no `WebSocketPair` at all
    (`ReferenceError: WebSocketPair is not defined`), a gap not in gaps.md.
  - `-unknown`: workerd refuses `No such compatibility flag: no_such_flag`; celld ignores it.
  - `-node-compat`: workerd hides `process` and `node:*` without `nodejs_compat`
    (`Failed to start Worker:` …); celld always has both. cellb fails to build `node:buffer` even
    with the flag.
  The two where celld lacks workerd's behaviour are judged by workerd (a reason of the kind
  conformance.md asks for: celld ignores the loaded Worker's flags).
- **`getDurableObjectClass(name, { props })`.** In the vendored `facets` test cellb gives `{}` as
  `ctx.props`; workerd passes it; celld refuses the stubs in it. With props passed, `facets` fails
  further on: it starts a facet inside the loaded Worker's isolate from a `ctx.exports` class of
  the host, which crosses into an isolate as a plain stub. So `facets` stays in
  `wd-worker-loader-gaps` (no golden re-recorded), and the proof is a new project
  `worker-loader-props` (judged by workerd: celld refuses the stub in the props).
- **`compatDateFlags`** needs compatibility dates (`Request`'s `cache` option before 2024-11-11),
  which cellb does not honour anywhere: it stays in `wd-worker-loader-gaps`, reason sharpened.

## Tasks

### T1 (F13) — `sql.exec()` refuses a script that does not end in a statement
- Red: `test/p09-celld-conformance.test.ts -t sql-exec` (new project and goldens).
- Fix: `endsInStatement()` in `src/core/sql-split.ts`, checked by `exec()` in `src/core/sql-storage.ts`.
- `wd-sql-default` stays a knownGap: cellb now stops at the same assertion as celld (ingest's
  syntax error); celld's own `assert.throws` rethrows that error with its stack frames where
  Node's reports a pattern mismatch. Reason reworded in scenarios.ts and gaps.md.

### T2 (F14) — `getDurableObjectClass(name, { props })` passes its props
- Red: new project `worker-loader-props` (judge workerd), Node and Chromium (isolates), and
  `test/p10h-loaded-class-props.test.ts` (the same project with the class in the project's realm).
- Fix: `src/bindings/worker-loader.ts` (the handle resolves with `props`; an isolated class
  carries them); `src/isolate/host.ts` and `src/isolate/isolate.ts` (props with each object
  message; the isolate's runtime gives them to the facet's `ctx.props`, through a per-class
  `props(cellKey)` option of `createCellRuntime`).

### T3 (F15) — loaded Workers have the Workers globals, and their own `websocket_standard_binary_type`
- Red: `worker-loader-flags-binary-type` (Node thread: `WebSocketPair is not defined`).
- Fix: the Node thread's bundle and the browser loaders give loaded code the Workers globals
  (`Request`, `Response`, `WebSocket`, `WebSocketPair`, …), with `WebSocketPair` per the
  WorkerCode's flag (`workersGlobalsFor(flags)`; the load message carries the flags).
- Also in the project's realm: `LOADED_IN_REALM` scenarios run with `isolatedModules: undefined`
  in `test/p10h-loaded-in-realm.test.ts` and without `isolateScript` in both browser specs.

### T4 (F16) — an unknown flag in `WorkerCode.compatibilityFlags` is refused
- Red: `worker-loader-flags-unknown` (judge workerd).
- Fix: `src/bindings/worker-loader.ts` checks the flags against the ones cellb knows (one list,
  shared with `createProjectRuntime`) before loading: `No such compatibility flag: <flag>`.

### T5 (F17) — `nodejs_compat` per loaded Worker
- Red: `worker-loader-flags-node-compat` (judge workerd).
- Fix: with the flag, `node:*` resolves and `process` exists; without it, `process` is undefined
  and a `node:*` import fails with `Failed to start Worker:`. Node loaders (`bundleWorker`,
  the thread bundle) and browser loaders (Blob-URL modules; site modules if the per-load
  module server can take the flag cleanly, else a gaps.md entry).

### T6 (F18) — `env`/`exports` for a Worker loaded into a site project's realm
- Red: `e2e-browser/site-projects.spec.ts`, the in-realm case expects the loaded Worker's own.
- Fix: the registry already tells loaded code from the project by the `<site>loaded/` prefix on
  the stack; the id after it names the load, whose scope `siteModuleLoader` registers.
  If that is not clean, the gaps.md reason is sharpened instead.
